# Adopción de GitHub Projects como sistema de gestión

## Contexto

Después de evaluar Jira Free y decidir no continuar con su implementación, LAPIN necesitaba encontrar una herramienta de gestión que pudiera representar su modelo de trabajo sin obligarnos a modificarlo para adaptarnos a las limitaciones de una plataforma.

La experiencia anterior había dejado un aprendizaje fundamental: disponer de muchas funcionalidades no garantiza que una herramienta sea adecuada.

El siguiente paso consistió en buscar una alternativa que permitiera gestionar el trabajo de LAPIN de forma práctica, con la menor complejidad y el menor costo posibles.

## Incorporación de GitHub Projects

Se adoptó **GitHub Projects** como sistema de gestión del trabajo de LAPIN.

La decisión respondió a su mayor adecuación práctica a las necesidades de esta etapa, especialmente frente a las dificultades encontradas durante la experiencia con Jira Free.

GitHub Projects permitió organizar el trabajo mediante Issues y visualizarlo a través de un tablero, manteniendo la relación entre las actividades gestionadas y el repositorio documental de LAPIN.

Su utilización también permitió avanzar hacia una estructura de gestión basada en los parámetros definidos por el modelo de LAPIN.

## Separación entre gestión y documentación

Con esta incorporación se consolidó una distinción importante:

**LAPIN HUB** conserva la documentación, las decisiones, los procedimientos y el conocimiento generado.

**GitHub Projects** permite organizar y dar seguimiento al trabajo necesario para producir esos resultados.

Ambos cumplen funciones complementarias.

Una actividad puede gestionarse mediante un Issue y producir como resultado uno o varios documentos conservados en el repositorio.

Esto evita utilizar los documentos como sustitutos de un sistema de seguimiento de tareas.

## Adaptación al modelo de LAPIN

Una necesidad particular de LAPIN es identificar el **Rol responsable** de una actividad, independientemente de la persona que opere la herramienta.

También necesitamos distinguir tipos de trabajo, prioridades, estados, estimaciones, períodos y relaciones entre actividades.

Estas necesidades se encuentran definidas en el documento `02-Estructura-y-configuracion-del-sistema-de-gestion.md`.

La incorporación de GitHub Projects permitió utilizar esa definición como referencia para organizar la gestión.

El objetivo no fue aprovechar todas las funcionalidades disponibles, sino implementar aquellas que respondieran a necesidades concretas.

## Criterio de costo y simplicidad

LAPIN se encuentra en una etapa de construcción y experimentación.

Por eso, una herramienta no se evalúa únicamente por sus capacidades técnicas. También importa cuánto tiempo requiere aprenderla, configurarla, mantenerla y utilizarla.

El costo económico es otra dimensión de la decisión.

En esta etapa, se priorizan alternativas gratuitas que permitan trabajar eficazmente sin introducir complejidad innecesaria.

La experiencia con Jira demostró que una herramienta puede tener un costo monetario bajo y, aun así, resultar costosa en tiempo de implementación.

GitHub Projects resultó una alternativa más práctica para las necesidades actuales de LAPIN.

## Qué aprendimos

La experiencia permitió reforzar varios criterios:

- Una herramienta debe evaluarse utilizando el modelo real de trabajo.
- La facilidad de implementación y operación importa tanto como las funcionalidades disponibles.
- El costo debe contemplar dinero, tiempo y esfuerzo de mantenimiento.
- No es necesario implementar todas las capacidades de una plataforma.
- La documentación y el seguimiento operativo deben mantenerse relacionados, pero con responsabilidades diferenciadas.
- La elección de una herramienta corresponde a una etapa concreta y puede revisarse cuando cambien las necesidades.

## Decisión

Se adoptó **GitHub Projects como sistema de gestión del trabajo de LAPIN**, manteniendo LAPIN HUB como repositorio de documentación y conocimiento.

La elección no implica que GitHub Projects sea una solución definitiva.

Su continuidad dependerá de que siga representando adecuadamente el modelo de gestión y permita trabajar con una relación razonable entre utilidad, esfuerzo y costo.

> **El modelo de LAPIN define cómo trabajamos. La herramienta nos ayuda a hacerlo, sin convertirse en el objetivo del trabajo.**

## Continuidad de la experiencia

La incorporación de GitHub Projects permitió avanzar en la organización del trabajo y consolidar su relación con la documentación del repositorio.

Las experiencias posteriores de edición local, utilización de VS Code, control de versiones con Git y publicación mediante commits corresponden a una nueva etapa de esta historia y se documentarán por separado.
